## Decisions

1. **One migration for the release**, `vocab_profile`, made after slice 4 with the schema of slices 1–4 (§4 asks for one; slice 1 lists "migration"). Later slices changed no schema (drift check).
2. **The seed of the bundled ontologies is one function, `seedOntologies`**, run by the migration and, when a bundled ontology or its terms are missing, by the first vocabulary call of a process (dev and tests push the schema and run no migration; a `truncate … cascade` of projects also empties `ontology-terms`). One small query when all are there.
3. **`concepts.list` is never empty but not `required` in the schema.** The hook gives an item with no list the list Topics of its project, and a new list Topics also makes the question Topics, as the migration does. So the old paths (the item form, SKOS import, the tests of other modules) keep working, and "a project with items in Topics asks Topics" holds everywhere.
4. **The served label of an item comes from `vocabulary.item`** at each rebuild (as today's tag labels); the stored `value` stays as the member saved it. An IRI that is no longer an item keeps its stored text (today a gone tag left the served story; now the delete guard refuses that delete).
5. **`story-values.story` is a foreign key to `stories`**, so a truncate of stories empties it too; the rows go in the stories `beforeDelete` hook, and are written in `afterChange` from the newest version and the main row (raw SQL, `.claude/rules/stories-raw-sql.md`).
6. **The migration rewrites the served representations by text** (parse, the same rewrite as the stored rows, `JSON.stringify`, a new ETag with `etagOf`) instead of a rebuild: up gives the bytes that this release's rebuild makes (tested), and down gives the bytes of the earlier release, which a rebuild with this release's code cannot make.
7. **JSON-LD writer (§9.3): hand-written** (`vocabulary/rdf.ts` `writeQuads`, expanded and flat, one `@graph` per named graph, no context). No new runtime dependency; `jsonld` 9.0.0 is a dev dependency for the tests only.
8. **The import endpoint reads and drops the rest of an over-limit body**, up to 4 × 5 MB, then answers 413: with an early 413, `next dev` reset the next request on the same connection.
9. **Search over the catalogue words**: `searchTerms` also matches the label and help of the catalogue question of a property, so "place" finds `dcterms:spatial` ("Spatial Coverage" has no "place").
10. **Admin markup uses the design system** (`design/design-system.md`): §2–4 of its stylesheet are in `custom.scss` once; every rule needs an `ao-*` class, so no other screen changed. The Annotate questions use the same components in `questions.css`, scoped to `.questions`, with the colours of the project tokens.

## Deviations from design/vocab.md

1. **Files per slice.** Several slices touched more than 5 files: a type change of `stories` (slice 3) reaches the Annotate page, the admin panel and 8 test files in the same change, or tsc is red; the admin slices also needed the project tab config, the sidebar, the view registration and the import map. Each slice still ended green.
2. **Names of files**: `vocabulary/rdf.ts` (all parsers and the writers) in place of `rdfxml.ts`; extra internal files `vocabulary/terms.ts`, `types.ts`, `files.ts`, `stories/linked.ts`, `stories/values.ts`; admin `VocabularyView.tsx`, `AddList.tsx`, `ListDownloads.tsx`, `classes.ts`; Annotate `answers.ts`, `questions.css`. `catalogue.ts` came in slice 1 (the search needs it).
3. **Additive interface members**: `vocabulary.item(…, { req })` (the rebuild reads inside the transaction of a relabel), `vocabulary.ontologies()`, `labels()` gives `valueType` too, `ThemeContext.labels`, `SkipReason 'other-list'`, `importSkos(…, { list })`, `exportSkos(…, listKey)`, `stories/index.ts` exports `storyValuesCollection`. The migration exports `valuesUp` and `valuesDown` for its test.
4. **The stored record has `modified`**, which §3.3 does not show (every story has it since Phase 1).
5. **jsonld.js compaction writes `dcterms:title` (a CURIE) for the `{ "id" }` of `rdf:predicate`.** The stored record keeps full IRIs (rule 3); the test checks that compaction differs only there and that expand(compact) equals expand. Both parsers give the same graph (URDNA2015).
6. **Theme JSON `fields` entries have `valueType` too**, so the widget makes a link only for a link question (an entity value is also an IRI). Additive (CONTRACT §3.2 rule 6).
7. **The sidebar job is Vocabulary**, as vocab.md §1 decides; concept-map §2.2 says "Questions". The screen heading is concept-map Q1 "Questions · {project}". The kind of answer offers vocab.md's six kinds (concept-map §3.8 lists "language" as a kind; here Language spoken is a list question). Q3's **Remove from the form** shows only for an unused question; a used one has **Hide from new stories** (the field lock). "Words and topics" (O10l) became "Words and subjects" (slice 11 done-when).
8. **Links must be `https:`** in answers (§3.1); the widget shows `http:` and `https:` links from other stacks.
9. **Omeka**: an entity list exports as `customvocab:{list}` (Custom Vocab can hold URIs), not `resource`, so the template round-trips; the import takes list or entity from the kind of the named list. `resource` without a list is read as an entity question with no list (left out).
10. **No drag in the Vocabulary tab**: **Move up** / **Move down** only (the keyboard fallback of §10).
11. **SKOS upload in the list page stays a Server Action (1 MB)**, as before; every other upload (and SKOS through **Load a vocabulary file**) goes through `POST /api/ontologies/import` (5 MB).
12. **Field usage reads `story-values`**: the newest and the published version, as §9.1 says. A value that only an older draft version has does not lock its field.
13. **MARC relators**: all 305 subjects are typed `owl:ObjectProperty` in `relators.nt`; the file has no `rdfs:subPropertyOf dcterms:contributor` triples (§2 says LoC declares them; not in this file).
