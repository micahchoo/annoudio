## Bug fix: `media.settled` stays active (found on the demo stack)

Symptom (demo stack `annoudio-demo`, production image): the worker reported `media.settled` for the upload `a0fabef2-…` (ready). After a restart with `ANNOUDIO_MEDIA_CONSUMER=1`, the job went to `active` at 16:15:46Z, 2 s after the container started. The `media` row stayed `uploaded`. No log line. No lock or waiting query in `pg_stat_activity`.

Root cause: the consumer started in Payload `onInit`. Every process that loads `payload.config.ts` runs `onInit`, not only the Next server. The image entrypoint runs `payload run deploy/migrate.ts` first, with the same environment. So the migrate process started the consumer. Its pg-boss took the waiting report (state `active`), and then the script called `process.exit(0)`. The handler never ran to the end, and nothing told pg-boss. An active job waits for its expiry, 900 s (the pg-boss default), before a retry. The timing proves it: the job started at 16:15:46, between "[migrate] waiting for the migration lock" and "[migrate] done", before Next was ready.

A second fault, from the same cause: in `next start`, `onInit` runs on the first `getPayload` call, so on the first request. After a restart with no visitor, nobody took the reports.

Why the tests did not find it: the int test starts the consumer by hand in a process that stays alive, and the e2e server is `next dev`, which calls `getPayload` for the first test request. No test ran a second process that loads the config and exits.

Fix:
1. `src/instrumentation.ts`: Next calls `register` once, when the server starts, before it takes requests. It does not run in `next build`, in `payload run` or in the tests. With `ANNOUDIO_MEDIA_CONSUMER=1` it calls `startConsumers()` (new export of `payload.config.ts`). `onInit` is gone from the config. Checked on `next start` of a production build: the log has "[jobs] The media.settled consumer is started." with no request.
2. One log line per report: "[media] media.settled: <id> is ready." (or "… No row changed: …" for a repeated report or a deleted row). An error writes "[media] media.settled: <id>: the update failed." with the error, and throws, so pg-boss gives the report again.
3. `worker/src/settled.ts`: the queue policy has `expireInSeconds: 60` (the handler is one row update). `workSettled` calls `updateQueue`, so a stack of an older release gets the policy at the next app start. A report that a stopped process took now comes back after about 60 s, not 15 minutes.

Tests: `tests/int/media/consumer.int.spec.ts` (2). It sets `ANNOUDIO_MEDIA_CONSUMER=1`, loads the config and starts Payload as the migrate script does, sends a real `media.settled` job through pg-boss, and checks that the job stays `created` and the row `uploaded`. Then it calls `startConsumers()`, as the server does, and checks that the row is `ready` and the job `completed` within 8 s, with the log line. With the consumer back in `onInit`, both tests fail (checked). Worker: `tests/settled.test.ts` gets one test: a queue of 900 s gets 60 s when the app starts to work it.

For the demo stack (not changed here): its image has the old code. The stuck job expires at about 16:30:46Z; then the consumer of its Next process (started by the first request at 16:16) takes the retry. The fix reaches the demo only with a new app image and a new worker image (`deploy/`). Note for the owner of `deploy/`: `ANNOUDIO_MEDIA_CONSUMER` now has effect only in the `next start` process; the migrate script can keep the same environment.

## Decisions

1. **A `mail` module, not `membership.Mailer.send(kind, to, data)`.** The port stays a transport: `send(message)` with `kind`, `to`, `subject`, `text`, `html`, `fromName`. Two adapters (SMTP, memory) need no knowledge of mail kinds; the kinds and their text live above the port, in one strings file (`mails.ts`). `membership` owns the login code, not the story mails: M2–M6 need story data, and a `membership` that knows stories would invert the dependency. `createNotices` gets its lookups as functions (`contact`, `projectName`, `recordingTitle`, `operators`, `waiting`), so `mail` reads no collection of another module. `kind` on each message lets tests and logs find a mail.
2. **`skipVerify: true` on the nodemailer adapter.** The adapter checks the SMTP connection when the config loads. Every process loads the config (`payload run`, `next build`); a check there makes network calls and log errors in places that send no mail. A failed send at use time still logs.
3. **"After the commit"** holds because every story mail comes from a `stories` method, after its Payload call returns (each local API call commits its own transaction), or after `commitTransaction` in `remove`. No mail goes from a hook. So every operator action of the review screen calls `stories` (Publish, Return, Remove), not Payload's own publish or delete; Payload's delete of stories is closed.
4. **The digest consumer has the guard of the media consumer.** `ANNOUDIO_MEDIA_CONSUMER=1` already names "the one app process that works jobs", and `deploy/` sets it. A second variable needs a change in `deploy/`, which is outside this task, and a stack that forgets it gets no M6. Its own pg-boss pool (max 2). The worker image must be rebuilt for the schedule.
5. **`lifecycle` is a pure function of a small row** (`LifecycleRow`: `reviewState`, `pendingRevision`, `rejection.automatic`, `mediaState`). `OwnDraft` and `StoryReview` have this shape, so `lifecycle(own)` and `lifecycle(review)` work as they are; `counts`, the list column and `nextWaiting` build the same row from the stored columns. Writing and Removed have no row, so the function knows the stored states: Processing, Waiting, Returned, Returned (automatic), Published, and the three states of a change to a published story. A failed file with no rejection yet is "Returned (automatic)": the member must act.
6. **M6 "for each story" goes when a story starts to wait** (the `waiting` event), not at every H4: a story with a voice note waits only after the worker settles it, and a mail for a story that cannot be published yet asks the operator for nothing. A save that `publish-at-once` publishes sends no M6.
7. **The badge of the sidebar is cached for 30 s and cleared by each story event of the process.** So the badge is exact after a publish, a return or a removal in the admin; a story that a member sends shows within 30 s.
8. **Walkthrough accessibility fixes go into our own CSS and components**, not into `node_modules`: the colours of Payload's descriptions and list headings, our document tab component, and the hidden selection column of the stories list. The other Payload lists keep their selection checkboxes (not on the walkthrough; see Not verified).

## Deviations from ia.md

1. **`stories.processing`, a sixth story field** (ia.md §8 lists five). The Processing tab of the review list (O4) is a Payload list filter, and a `where` reads stored columns only. The media state lives in `media`. So `stories` keeps a stored copy for the newest version: the `recordChange` hook writes it on each save, and `mediaSettled` changes it when a body settles. `counts` reads the same column, so a tab and its count agree.
2. **Four operator fields** in place of one: `reviewMail` (ia.md), and `name` (History says "Published by Ravi"; operators had only an email), `snippetPasted` (checklist step 3, **I pasted it**) and `checklistHidden` (**Hide the list**). One migration for the phase holds them all.
3. **Remove is a button after Publish, not in the ⋮ menu** (§4.1, O5c). Payload 3.90.2 shows the document menu only when the operator may create or delete (`DocumentControls`, `showDotMenu`). Stories have no create, and an open delete puts Payload's own Delete in the menu, which skips `stories.remove` (the replies, the files, M5). So the menu does not show, and **Remove** is a secondary button in the danger colour, last in the row, with a confirmation dialog.
4. **The review screen title is the story excerpt**, not "Story by Asha, 1:02–1:35" (§4.1, rule 3): `useAsTitle` cannot be a virtual field (Phase 5, decision 4). The crumb reads "Review stories / My father worked the ferry…".
5. **"Last 7 days" has no "removed" count.** A removed story has no row (§2.1: M5 is the record), so nothing can count it. The line says "12 came in, 9 published, 2 returned."
6. **"An int test derives all 7 states"** (slice 1): Writing and Removed have no row (decision 5). The lifecycle test derives the stored states, the three change states and the reply variant from real data, and all 36 inputs of the function.
7. **O0 keeps Payload's button word "Create"**; the heading and the intro are ours ("Welcome to Annoudio", "Make the first operator account: …"). `general:create` is the button of other screens too, and the view has no component slot (§9 flags it).
8. **Your stories shows each group as a section with its count**, not as closed `▸` disclosures (§4.2): every card is one Tab press away and nothing hides behind a control.
9. **The rights line has the label "Stories here:"** in the player and the Annotate footer ("Stories here: CC BY 4.0"). ia.md shows "Stories here are shared under CC BY 4.0."; that sentence is wrong for "All rights reserved" or an operator's own line. The Annotate page hides the player's own `rights` part (it shows the line once, in its footer).
10. **The time fields are text fields** (`1:02`, `1:02.5`, `62`), not number fields: a number field cannot take `1:02`. A stored time shows exactly (`1:02.5`), so a save without a change keeps it.
11. **A save with no valid `return` opens Your story** (the story with `story=<id>&saved=1`), where ia.md has a separate P5 "Sent" screen: one screen shows the state of the story after the save and later.
12. **The frontend template is removed**: `/` (Payload's "Welcome to your new project") redirects to Your stories, the member home; its template test now checks the redirect.
13. **The Recordings list has no create** (O8, as ia.md says) through closed create access: `catalogue.register` (the local API) makes recordings; the admin forms only change them.
